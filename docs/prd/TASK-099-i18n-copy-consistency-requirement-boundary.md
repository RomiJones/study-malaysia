# TASK-099 多语言文案一致性需求边界与验收补充

## 1. 文档信息

- **任务编号**：TASK-099
- **任务标题**：新增需求边界、验收标准和依赖规划补充：多语言文案一致性拆分
- **运行编号**：TASK-099-2026-05-25T13-45-24-384Z
- **父任务**：TASK-067
- **父任务新增需求**：后端接口返回的数据是多语言不太对，很多都是中文而已，但是前端却显示对应的都是多语言正常；不仅前端多语言正常，学校和专业等数据也需要以多语言正常版本入库。
- **当前子任务定位**：只处理用户端 i18n key、硬编码文案、运行时文案兜底和语言切换一致性检查的需求边界、验收标准、依赖规划和本地验证记录。
- **事实来源说明**：Notion 是中文项目文档和任务管理来源，不是业务数据库；本地 Markdown 快照只作为本轮可写入记录，不使用 `task.json` 作为任务事实源。

## 2. 目标和用户价值

TASK-099 的目标是把父任务 TASK-067 中与“前端多语言文案一致性”相关的部分单独收口，确保用户端支持的语言在界面文案、动态字段 fallback、错误提示和语言切换后状态中不出现明显混合语言、缺失 key、硬编码文案或后端原始错误直出。

对用户的价值是：用户切换到简体中文、繁体中文、英文或马来文后，导航、筛选、院校详情、专业详情、规划、收藏、对比和登录错误等核心路径都应使用当前语言的自然表达；即使后端数据暂时缺少完整多语言字段，前端也不能把中文动态内容直接渲染到英文或马来文页面，也不能把英文后端错误直接透出到中文界面。

对产品和工程的价值是：TASK-099 明确前端 i18n 防线与后端多语言数据治理之间的边界。前端可以通过 key 完整性、硬编码扫描、动态文案清洗和浏览器回归证明“展示层没有明显混合语言”；但学校、专业等业务数据的多语言入库、字段映射、导入和 API 契约仍由数据模型、后端 API 和集成验证子任务承担。

## 3. 支持语言边界

当前用户端和共享契约支持的语言列表为：

- `zh-CN`：简体中文。
- `zh-TW`：繁体中文。
- `en`：English。
- `ms`：Bahasa Melayu。

TASK-099 不新增、不删除语言，也不改变语言代码。后续如果产品要求新增语言或变更语言代码，应先更新共享语言契约、用户端 i18n 消息、后端偏好接口和测试脚本，不应在页面中局部硬编码。

## 4. 功能范围

TASK-099 覆盖以下前端 i18n 一致性范围：

- 四语言 `messages` key 结构一致，不能存在缺失 key、额外 key 或空字符串值。
- 用户端 Vue 模板中的用户可见文本应使用 i18n 绑定或明确允许的品牌、缩写、单位和年份，不应直接写死可翻译文案。
- 脚本中生成的可见筛选标签、预算标签、状态标签和动态说明应走统一 formatter 或 i18n key，切换语言后能即时更新。
- 后端返回的原始分类值、专业方向、院系、申请说明、开学时间、语言要求、官方备注和学制说明在当前语言下要么被本地化，要么回退到当前语言的官方页面提示，不能把不匹配语言的原文直接展示给用户。
- 英文和马来文界面不得直接显示中文动态数据；繁体中文界面不得出现已知简体残留；中文界面不得直接显示后端英文错误信息。
- 用户端错误态应优先使用本地化错误 key 或已知错误映射，后端 `error.message` 只能用于调试或日志，不应作为用户可见文案直接渲染。
- 语言切换一致性应覆盖当前语言下的导航、筛选、院校详情、专业弹窗、规划、收藏、对比、登录弹窗和费用/推荐工具入口。

## 5. 非目标

- TASK-099 不负责学校、专业、费用、要求等业务数据的多语言入库，不创建数据库迁移，不执行导入脚本，不修改种子数据。
- TASK-099 不负责后端 API 返回多语言字段的契约设计、字段校验或错误响应结构；这些范围应由 TASK-096、TASK-097 或父任务后端相关子任务处理。
- TASK-099 不负责重做用户端语言切换入口、顶部菜单间距或响应式布局；这些属于 TASK-059 至 TASK-062 及 TASK-098/TASK-100 的用户端和集成验证范围。
- TASK-099 不翻译官方学校名、官方专业名、QS、IELTS、TOEFL、GPA、MQA、RM、CNY、URL 或官方来源标题等可保留原文的专有名词。
- TASK-099 不关闭真实 Notion Review issue；本轮只能根据本地代码和脚本判断相关问题是否仍可复现，并在本地记录验证结论。

## 6. 与父任务和其它子任务的关系

- 与 TASK-067 的关系：TASK-067 是父级新增需求边界任务；TASK-099 只承接其中“前端多语言文案一致性检查”的子范围，不替代父任务中的数据入库和后端多语言要求。
- 与 TASK-096 的关系：TASK-096 应处理学校、专业等数据模型和数据准备中的多语言字段、迁移、导入或种子数据验证。TASK-099 不能用前端 fallback 替代数据层治理。
- 与 TASK-097 的关系：TASK-097 应处理后端 API、服务、校验和错误处理中的多语言契约。TASK-099 只验证用户端不直接暴露不匹配语言或原始错误。
- 与 TASK-098 的关系：TASK-098 负责用户端页面和交互落地。TASK-099 提供 i18n 文案一致性的检查边界，可作为用户端实现时的质量门槛。
- 与 TASK-100 的关系：TASK-100 负责最终集成验证和 Review。TASK-099 的脚本验证结果应被纳入最终集成验收，但不能替代全页面浏览器验证。
- 与 TASK-030、TASK-040、TASK-041、TASK-042 的关系：这些历史任务提供四语言文案、审计脚本和多语言视觉回归基线。TASK-099 复用这些脚本和报告作为验收依据。

## 10. 依赖规划

当前 TASK-099 没有真实前置任务；它可以在 `parallelGroup=i18n`、`lockScopeHint=module_scope` 下独立完成文档边界和本地专项验证。

后续真实依赖应按能力判断，而不是按任务编号机械串联：

- 若要证明“业务数据本身多语言正常入库”，必须等待 TASK-096 的数据模型和数据准备结果，以及 TASK-097 的 API 契约结果。
- 若要证明“用户端所有页面切换语言后无混合语言和布局问题”，必须等待 TASK-098 的页面实现范围稳定，并由 TASK-100 执行全页面浏览器验证。
- 若后端仍只能返回中文业务字段，TASK-099 的前端 fallback 只能防止界面混合语言，不等于完成父需求中的多语言数据治理。
- 若 Review 快照仍显示 i18n open issue，后续应由 Review 流程依据脚本和浏览器证据更新状态，避免长期保留过期风险。
