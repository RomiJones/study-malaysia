## 2. 目标和用户价值

本新增需求的目标是修复用户端首页中“专业方向”筛选条件被遮罩、遮挡或层级覆盖的问题，确保用户在首页筛选专业方向时可以清楚看到全部可选项、选中态和清除状态，并且可以通过鼠标、键盘和移动端触控稳定完成筛选。

对用户端的价值是：用户进入首页后可以直接按专业方向缩小院校或专业范围，不会因为选项被遮住、点击区域被覆盖、浮层被裁切或文字重叠而误判筛选不可用。对产品体验的价值是：首页是核心转化入口，专业方向筛选需要与搜索、Hero 快捷入口、院校列表和活跃筛选标签共同工作，视觉层级必须清晰、稳定且符合静态页面视觉基线。

## 3. 问题边界

当前问题聚焦在首页专业方向筛选条件的可见性和可操作性。这里的“遮罩情况”需要在后续技术方案和实现任务中进一步复现并定位，可能包括但不限于以下表现：

- 专业方向选项被搜索建议、Hero 层、筛选面板、活跃标签、sticky 元素或其它浮层遮挡。
- 专业方向下拉、展开列表、标签组或筛选按钮被父容器 `overflow` 裁切，导致选项显示不完整。
- 可见文字虽然没有被遮住，但实际点击区域被透明遮罩或高层级元素拦截，导致无法选择或误触。
- 移动端窄屏下专业方向筛选项与其它控件重叠、换行异常、横向溢出或被底部/顶部浮动元素覆盖。
- 多语言切换后，专业方向文案长度变化造成按钮、标签或浮层被挤压，从而再次出现遮挡。

本需求不预设根因是 `z-index`、`overflow`、布局高度还是组件结构问题；后续 TASK-056 应先确认复现路径、目标 DOM 和影响范围，再给出实现方案。

## 4. 功能范围

### 4.1 覆盖页面和控件

后续实现应只覆盖用户端首页中与专业方向筛选直接相关的展示和交互区域：

- 首页专业方向筛选入口、选项列表、展开态或下拉态。
- 专业方向选中态、取消选择、清除筛选和活跃筛选标签展示。
- 与专业方向筛选发生层级冲突的首页相邻元素，例如搜索建议、Hero 快捷分类、筛选容器、院校列表首屏和移动端浮动区域。
- 如确认为共享筛选组件造成问题，修改范围应限定到首页使用场景，或在 TASK-056 中明确共享组件影响面和回归范围。

### 4.2 后续实现应覆盖的体验点

- 专业方向筛选选项在桌面端、平板和移动端都完整可见，不被遮罩、裁切、重叠或透明层拦截。
- 筛选选项的点击、键盘 focus、hover、active 和已选择状态具备明确反馈。
- 下拉、popover 或展开区域应处于合理层级，不压住不该遮挡的主操作，也不被其它元素覆盖。
- 修复不得破坏首页搜索建议、Hero 快捷入口、院校卡片、活跃筛选标签、分页或路由查询参数。
- 多语言下专业方向文案应继续使用既有 i18n 或格式化能力，不新增硬编码中文或英文。
- 如果专业方向筛选与搜索结果或 API 查询有关，后续实现不得静默改变筛选语义、分类值、接口参数或结果数量，除非 TASK-056 明确确认这是必要修复范围。

## 8. 后续实现验收口径

后续 TASK-057 实现时，至少需要满足以下验收口径：

- 首页专业方向筛选条件在默认态、展开态、选中态和清除后都不被遮罩、裁切、重叠或透明层拦截。

## 11. 风险和后续实现边界

- 只提高 `z-index` 可能掩盖根因，并可能破坏搜索建议、移动导航、弹窗或其它浮层的层级顺序。
- 只修改 `overflow` 可能让下拉选项可见，但也可能造成首页横向溢出或相邻模块被覆盖。
- 移动端遮挡通常与视口高度、软键盘、滚动位置和触控命中区域相关，后续实现不能只验证桌面端。
- 专业方向文案在多语言下长度不同，修复需要用真实语言验证，而不是只看简体中文。
- 当前项目仍存在首页、筛选和分类相关的历史 Review 问题；后续实现和 Review 需要区分本需求范围与历史问题，避免把其它未完成范围混入 TASK-055 的验收结论。
