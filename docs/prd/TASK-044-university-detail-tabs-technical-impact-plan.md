## 2. 需求边界

本轮技术分析只覆盖用户端学校详情页的一级内容 tab：

- 概览
- 本科专业
- 硕士专业
- 博士专业
- 校园设施
- 申请信息

本需求的目标是增强这组 tab 的当前态识别、点击反馈、响应式可用性和整体美观度，不改变 tab 代表的业务内容、不改变专业筛选规则、不改变公开展示状态、不改变后端返回结构。

后续 TASK-045 实现时应优先在静态页面视觉 token 内做增强。如果“重新设计”被理解为完全偏离静态 HTML 详情页标签样式，应先请求产品确认，不应在实现任务中直接推翻既有 1:1 视觉基线。

## 3. 当前实现基线

当前学校详情页 tab 位于用户端单页实现中：

- `apps/web/src/pages/UniversityPage.vue`
  - 模板中使用 `.detail-tabs` 和 `.detail-tab` 渲染六个按钮。
  - `activeTab` 是本页本地状态，类型为 `"overview" | "bachelor" | "master" | "phd" | "facilities" | "apply"`。
  - `detailTabs` 通过 `t('university.*Tab')` 读取现有 i18n 文案。
  - `setActiveTab` 只切换本地 tab 并关闭专业详情弹窗。
  - 页面切换院校 slug 时会把 `activeTab` 重置为 `"overview"`。
- `apps/web/src/style.css`
  - `.detail-tabs` 和 `.detail-tab` 已有基础下划线式样式。
  - 当前选中态主要依赖文字变白和金色底边，识别度有限。
  - 移动端媒体查询中 `.detail-tabs` 使用换行，`.detail-tab` 按三列分布，长文案依赖 `overflow-wrap: anywhere`。
  - 文件中仍存在早期 `.detail-tabs a` 选择器片段，当前模板使用 button，该片段对现有 tab 不生效；若 TASK-045 调整同一区域样式，可以在确认无引用后作为同范围清理项处理。
- `apps/web/src/i18n/messages.ts`
  - 已存在英文、简体中文和马来文 tab 文案。
  - 本需求默认不新增文案；如增加辅助说明、aria label 或 tooltip，必须补齐所有支持语言。

## 5. 接口、数据结构和状态影响

### 5.1 接口影响

本需求不需要新增或调整 API。学校详情页 tab 的展示完全由前端已有 `detailTabs` 配置、i18n 文案和本地 `activeTab` 状态驱动。

后续实现不得为了展示 tab 数量徽标而临时修改接口或写死 UM 专业数量。若产品确认需要在本科、硕士、博士 tab 上展示数量，应优先复用当前详情响应中的 `detail.programs` 聚合计算；如果需要后端 facets 或不同公开状态统计，应拆成独立任务评估。

### 5.2 数据结构影响

现有 `DetailTab` 联合类型可以继续使用，不需要新增共享枚举或后端 DTO。后续实现可以在 `detailTabs` 前端视图模型中临时增加仅用于 UI 的字段，例如：

| 字段 | 用途 | 约束 |
| --- | --- | --- |
| `key` | tab 状态键 | 继续使用现有六个值，不增加业务含义。 |
| `label` | 当前语言展示文案 | 必须来自 i18n。 |
| `panelId` | 关联 `aria-controls` | 仅用于前端可访问性，不进入 API。 |
| `count` | 专业数量徽标 | 仅在产品确认后添加；不能写死 UM 数量或静态 Demo 数量。 |

### 5.3 前端状态影响

`activeTab` 仍是学校详情页内部状态。后续实现默认不把 tab 状态写入 URL、localStorage 或后端。如果需要支持刷新后保留 tab、分享指定 tab 或滚动吸顶后高亮，应另开任务，因为这会影响路由、可分享链接和回退行为。

## 6. 推荐实现方案

### 6.1 视觉方案

建议将当前细下划线 tab 增强为更明确的学校详情页分段导航：

- 外层 `.detail-tabs` 使用深色 Hero 内的半透明容器或柔和分隔条，保持与 `#0C0E1A`、`#C8A84B`、白色透明度体系一致。
- 每个 `.detail-tab` 保持 40px 以上点击高度，桌面端可使用胶囊或分段按钮形态，当前态使用背景、边框或底部强调线组合，不只依赖文字颜色变化。
- 选中态建议至少包含两种反馈：更高对比文本色、金色强调线或浅金背景；hover/focus 使用较弱但可见反馈。
- 不引入大面积紫色、蓝色渐变、强装饰背景或与 StudyMY 视觉 token 不一致的新色系。
- 不将 tab 放进新的大卡片嵌套卡片；该导航仍应属于详情 Hero 和内容区之间的一级导航。

### 6.2 交互方案

后续 TASK-045 应保持现有切换逻辑：

- 点击 tab 只切换 `activeTab`。
- 切换 tab 时继续关闭专业详情弹窗，避免弹窗内容与当前栏目不一致。
- 切换院校 slug 时继续重置到概览。
- 不修改 tab 下方内容的排序、筛选或数据来源。

可以增强的交互：

- 为 active tab 增加 `aria-selected="true"`、非 active tab 增加合理 `tabindex`。
- 为 tab 和内容 panel 增加稳定 `id`、`aria-controls`、`aria-labelledby`。
- 支持键盘左右方向键切换 tab，并让 focus 状态清晰可见。
- 在移动端保持横向滚动或两行网格时，需要提供足够点击目标和当前态可见性。

### 6.3 响应式方案

桌面端建议保持单行展示，避免六个 tab 占用过高垂直空间。窄屏与移动端可二选一：

1. 横向滚动 tab：适合保留单行层级；需要确保有滚动提示、当前项不被截断、整页不出现横向溢出。
2. 两行或三列分段布局：适合六个固定 tab；需要确保英文和马来文长文案不挤压、不会出现文字重叠或过高跳动。

当前移动端已有三列换行基础，TASK-045 可以在此基础上增强选中态和间距。若改为横向滚动，应重点验证 390px、600px、760px 和 900px 视口。

### 6.4 多语言和可访问性

后续实现必须继续通过 `t('university.*Tab')` 获取 tab 文案。英文、简体中文、繁体中文和马来文页面都不能出现硬编码混用；现有 Review 中与动态分类翻译相关的问题不属于本需求，但 TASK-045 浏览器验证时应记录它们与 tab 样式无关。

可访问性最低要求：

- tablist、tab 和 panel 语义完整。
- 当前 tab 有明确 `aria-selected`。
- focus-visible 不被隐藏。
- 颜色对比满足深色背景可读性。
- 移动端点击区域不小于常规可点控件尺寸。

## 8. 风险和控制方式

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| tab 样式选择器过宽 | 误伤规划页、登录弹窗或其他 tab 样式 | 使用 `.university-detail-page .detail-tabs` 或等价范围限定。 |
| 选中态过度设计 | 破坏静态 HTML 视觉一致性 | 只使用既有 token 和轻量视觉反馈，避免新色系和重装饰。 |
| 移动端英文或马来文过长 | 文本溢出、换行拥挤、点击目标过小 | 用真实语言验证 390px、600px、760px 视口，必要时横向滚动或紧凑两行布局。 |
| 清理旧 `.detail-tabs a` 选择器误删其他引用 | 造成历史样式缺失 | 清理前用 `rg` 确认当前模板没有 `.detail-tabs a` 结构；只在同一功能范围内删除。 |
| 添加专业数量徽标 | 引入数据依赖和统计口径争议 | 默认不做；必须产品确认后才实现，并由现有详情数据计算。 |
| 增加 URL tab 状态 | 改变路由和分享行为 | 默认不做；如需要另开任务。 |
| 只运行构建不做浏览器验证 | 无法发现真实溢出和焦点问题 | TASK-045 必须做浏览器验证和截图，至少覆盖桌面与移动端。 |
