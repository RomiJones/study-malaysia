## 2. 目标和用户价值

本新增需求的目标是提升学校详情页核心内容区标签切换的可识别性和可用性，让用户能清楚判断当前所在栏目，并快速在概览、本科专业、硕士专业、博士专业、校园设施和申请信息之间切换。

对用户端的价值是：用户浏览学校详情时不容易迷失当前位置，能够更快定位专业层级、设施信息和申请信息；在移动端或内容较长时，标签导航需要帮助用户减少滚动和反复查找。对产品体验的价值是：学校详情页作为高频决策页面，标签样式应与静态页面视觉基线一致，同时比当前实现具备更明显的选中态、层级感和交互反馈。

## 3. 问题边界

当前问题聚焦在学校详情页内容区 tab 切换不够明显，主要表现为：

- 用户难以快速分辨当前激活的是概览、本科专业、硕士专业、博士专业、校园设施还是申请信息。
- tab 作为详情页一级内容导航，但视觉层级、选中态、hover/focus 反馈和可点击区域不够突出。
- 移动端或窄屏下，如果标签横向排列、换行或滚动处理不佳，会降低用户切换效率。
- 不同语言下 tab 文案长度不同，后续实现必须避免文本溢出、按钮挤压或布局跳动。

本需求不改变 tab 背后的业务含义，只提升这组导航控件的展示和交互可用性。

## 4. 功能范围

### 4.1 覆盖页面和标签

后续实现应只覆盖用户端学校详情页的以下标签切换区域：

- 概览
- 本科专业
- 硕士专业
- 博士专业
- 校园设施
- 申请信息

除非 TASK-044 技术方案确认存在共享组件影响，否则不得扩展到全站其他 tab、管理端 tab、弹窗 tab 或筛选控件。

### 4.2 后续实现应覆盖的体验点

- 明确当前激活 tab：选中态应在颜色、底线、背景、边框、阴影或图标状态中至少有一种强识别反馈，不能只依赖细微文字颜色差异。
- 明确可点击区域：tab 应具备足够点击面积，鼠标 hover、键盘 focus 和按下态需要有可感知反馈。
- 保持视觉一致：样式应沿用静态页面视觉 token 和既有 StudyMY 用户端设计语言，不引入与页面主视觉冲突的全新色系。
- 保持内容结构：切换 tab 后仍展示原有对应内容，不删除、不合并、不重排已有内容模块。
- 保持响应式可用：桌面端、平板和移动端都应能清楚识别当前栏目；移动端可以采用横向滚动、分段控件或紧凑布局，但不得出现文本溢出或点击目标过小。
- 保持多语言兼容：实现时应继续使用现有 i18n 文案来源，不能新增硬编码中文或英文 tab 文案。
- 保持可访问性：后续实现应保留或补充 `aria`、键盘导航、focus 可见状态和语义化 tab/list 结构。

后续 TASK-045 实现时，至少需要满足以下验收口径：

- 学校详情页六个 tab 的当前激活状态清晰可辨，用户无需反复查看内容标题即可判断当前位置。

- 桌面端、平板和移动端都没有文本溢出、横向整页溢出、重叠、遮挡或布局跳动。

- 不改变 tab 对应内容、数据过滤逻辑、专业数量、路由行为或页面滚动上下文，除非技术方案明确说明并通过确认。
- UI 验证应覆盖学校详情页首屏和 tab 区域，必要时与静态 HTML 或既有验收截图对比。

## 9. 需要人工确认的问题

- “重新设计”是否允许偏离静态 HTML 原 tab 样式，还是必须只在静态页面视觉 token 内增强选中态和反馈。
- tab 是否需要展示专业数量，例如本科专业、硕士专业、博士专业旁边显示数量。
- 当某个学校没有对应层级专业、没有校园设施或没有申请信息时，tab 应隐藏、禁用还是保留空状态。
- 移动端是否接受横向滚动 tab，还是更倾向于分段控件、下拉选择或两行网格布局。
- 是否需要 tab 在详情页长内容滚动时吸顶，还是保持在内容区原位置。
- 是否需要同步调整静态 HTML 视觉参考文档，还是仅在 Vue 实现中做体验优化。

## 11. 风险和后续实现边界

- 样式增强可能影响全站共享 tab 或按钮样式，后续实现应优先限定选择器或组件范围，避免扩大回归面。
- 更明显的选中态如果过度使用高饱和色或大面积阴影，可能破坏学校详情页与静态视觉基线的一致性。
- 移动端 tab 如果只做横向滚动但没有滚动提示，用户可能仍然看不到后续栏目；需要在 TASK-044 中评估交互形式。
- 多语言文案长度会影响 tab 宽度，后续实现必须用真实语言切换验证，而不是只看简体中文。
- 如果加入专业数量或状态徽标，可能引入 API 数据依赖和加载状态问题；该能力需要在技术方案中单独确认，不应作为样式任务默认内容。
