## 2. 目标和用户价值

本新增需求的目标是把静态 HTML 中与马来大学（Universiti Malaya / UM）相关的院校、专业、费用、学制、入学要求、语言要求、申请材料、开学时间、官方来源、设施、申请信息和审计说明等数据，纳入 StudyMY 既有后端数据库的数据治理范围，避免用户端继续依赖静态页面内嵌数据或前端硬编码。

对用户端的价值是：学校详情页、专业列表、专业详情弹窗、搜索筛选、对比、费用估算和申请规划能够使用同一套可维护、可校验、可追溯的数据。对运营和管理端的价值是：UM 数据可以通过后台字段维护、核验和后续补录，而不是散落在静态 HTML、Markdown 或临时代码中。

## 3. 功能范围

### 3.1 本需求覆盖的数据对象

- 马来大学院校主档：学校名称、简称、类型、地区、排名、简介、图片、Logo、标签、学生规模、官方链接、国际招生链接、申请入口、联系方式、官方核验摘要。
- 马来大学专业数据：本科、硕士、博士专业的名称、层级、方向、院系、学习模式、校区、学制、开学时间、学费、币种、语言要求、学术要求、申请材料、课程或方向、职业方向、官方来源和公开展示状态。
- 马来大学校园设施和申请信息：静态页面中用于学校详情页展示的设施、申请说明、材料清单、申请步骤、官方说明和提示文案。
- 数据来源和审计字段：官方来源 URL、核验时间、来源优先级、费用核验状态、公开展示状态、不开放国际学生或隐藏未核验说明。

### 3.2 后续实现必须满足的产品边界

- 数据导入目标是 StudyMY 后端对应的运行时数据库，不是 Notion，也不是 `docs/notion-snapshot` Markdown 快照。
- 静态 HTML 只能作为本次 UM 数据提取的输入源；后续导入前必须生成 dry-run 报告，列出提取数量、字段缺失、重复项、公开展示状态、来源缺失和风险项。
- 导入必须保持已有历史任务和现有数据不被重置；不得为了导入 UM 数据删除其他学校、其他任务生成的数据或用户数据。
- 面向用户端展示时，公开列表只应使用满足公开展示条件的数据；隐藏未核验、不开放国际学生或来源不足的数据应保留在数据层或管理端核验流中，不应直接进入公开主列表。
- 费用、语言要求、申请要求等来自官方来源的字段必须保留原始官方文本或来源备注，不能只保留格式化后的展示文案。
- 如果静态 HTML 中同一字段存在中文展示值、英文官方值和审计备注，后续实现需要明确存储位置和展示优先级，不能把审计备注混入普通简介字段。

## 4. 非目标

- 本任务不执行数据提取脚本、不导入数据库、不修改实体、接口、前端页面或管理端页面。
- 本需求第一阶段不要求导入静态 HTML 中所有学校；除非后续人工确认，否则范围限定为马来大学（UM）相关数据。
- 本需求不重新设计学校详情页 UI、专业弹窗 UI 或标签页样式；相关 UI 需求仍归属既有前端任务或此前新增需求。
- 本需求不把 Notion、Markdown 快照、静态 HTML 文件或 `task.json` 作为业务数据库。
- 本需求不覆盖 TASK-001 至 TASK-050 的历史结论、执行记录、Review 问题或已完成任务。
- 本需求不直接决定 seed 数据、生产数据、测试数据的最终部署策略；这些策略需要在 TASK-052 和 TASK-053 中明确。

- 文档修改不包含业务代码、数据库迁移、数据导入或无关模块重构。

## 7. 需要人工确认的问题

- “马来大学所有数据”是否只指 Universiti Malaya / UM，还是也包含静态 HTML 中与 Malaysia 相关的其他院校数据。
- “对应的数据库”具体指本地开发 MySQL、测试环境数据库、生产数据库，还是只生成可审阅的 seed/import 文件。
- 是否允许导入隐藏未核验、不开放国际学生或缺少官方来源的数据；如果允许，这些数据是否只能进入管理端待核验状态。
- 对静态 HTML 中中文翻译字段、英文官方字段、审计备注和展示兜底文案，是否需要全部持久化，还是只持久化官方字段和来源。
- 导入后是否需要管理端审批发布流程，还是可以由导入脚本直接标记为公开可展示。
- 如果数据库中已经存在 UM 数据，应以静态 HTML 覆盖、增量补齐，还是保留现有数据并生成差异报告等待人工确认。

## 8. 阻塞条件

- 无法访问 `D:\mydev\StudyMY_UM_v58_na_display_tidy.html` 或无法解析其中 UM 数据时，后续实现必须阻塞并报告缺失路径或解析失败原因。
- 无法确认 UM 范围、目标数据库环境、覆盖策略或公开发布策略时，不允许执行真实写库导入。
- 字段映射不能覆盖费用、学制、语言要求、申请要求、材料、官方来源和公开展示状态等核心数据时，不允许宣称“所有数据已导入”。
- 发现导入会删除或覆盖非 UM 数据、用户收藏、规划、申请记录或其他任务数据时，必须阻塞并改为人工确认。

## 9. 风险和后续实现边界

- 静态 HTML 数据可能同时包含基础层、补充层和运行时合并层，后续实现必须区分来源层级，避免把演示补充数据误判为官方基础数据。
- “所有数据”容易扩大为全站全校导入；后续任务应先锁定 UM，再通过单独需求扩展到更多学校。
- 费用和语言要求存在官方原文、格式化展示值和审计说明，后续实现必须保留可追溯性，否则会影响用户信任和管理端核验。
- 数据导入任务可能触及数据库写入、迁移、种子数据和现有 API 契约，必须在 TASK-052 中明确回滚方案，并在 TASK-053 中以 dry-run 优先。
- 现有 Review 问题中存在与 TASK-004 数据模型记录不一致相关的问题；它们不属于 TASK-051 文档边界，但会影响后续数据导入验收可信度，应在后续实现和 Review 中继续跟踪。
