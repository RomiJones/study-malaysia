## 2. 目标和用户价值

本新增需求的目标是把智能推荐从“用户打开后直接给出默认或凭空匹配结果”调整为“登录用户基于本人学生画像获得专业推荐”的受控流程。用户必须先完成登录，并补齐足以判断推荐结果的学生画像信息，系统才能展示推荐专业、匹配理由、风险提示和后续规划入口。

对用户的价值是：推荐结果不再像静态演示或默认筛选一样泛化，而是能结合用户的目标学历、目标专业方向、预算、GPA、语言成绩、工作经验和是否接受后补语言等信息，给出更接近真实申请决策的专业组合。用户能理解为什么某个专业被推荐，也能看到需要补充材料、提升语言或调整预算的原因。

对产品的价值是：智能推荐模块从流量入口升级为登录和画像完善的关键转化点。它既能引导用户沉淀真实申请意向，也能为后续申请规划、材料清单、任务分层、咨询跟进和管理端维护规则提供可信数据基础，避免系统在缺少用户输入时生成看似智能但无法负责的推荐。

## 3. 需求边界

本需求聚焦智能推荐模块的登录前置、画像完整性前置和推荐结果来源约束。这里的“智能推荐模块”至少包括用户端顶部或浮动入口打开的智能推荐弹窗、规划页中的推荐结果区、以及后续可能复用同一推荐接口或推荐结果卡片的用户端入口。

后续实现应满足以下基本边界：

- 未登录用户点击智能推荐入口时，不展示专业推荐结果；应引导用户登录或注册。
- 已登录但学生画像未达到最低完整度时，不展示专业推荐结果；应引导用户进入或打开画像完善流程。
- 只有已登录且画像达到最低完整度的用户，才能看到基于画像计算的专业推荐结果。
- 推荐结果必须能追溯到用户画像字段和公开专业数据，不能使用无用户上下文的固定默认结果冒充个性化推荐。
- 如果推荐接口仍支持公共专业筛选查询，该能力必须与“智能推荐模块”区分命名、权限、入参和展示文案，不能让用户误以为匿名筛选是个性化推荐。

学生画像的最低完整度建议以 TASK-008 中已有画像字段为起点，后续技术方案需要确认最终字段和规则：

| 字段 | 作用 | 是否建议作为推荐前置 |
| --- | --- | --- |
| `level` | 匹配本科、硕士或博士等专业层次 | 是 |
| `targetCategory` | 匹配目标专业方向或专业类别 | 是 |
| `budget` | 判断年度成本或总成本是否超出预算 | 是 |
| `gpa` | 判断学术门槛和竞争力 | 是 |
| `ielts` | 判断语言门槛、语言风险和后补语言可能性 | 是 |
| `experience` | 判断硕博、职业型项目或咨询跟进优先级 | 可选，但建议纳入画像完整度 |
| `acceptNoLanguage` | 判断语言未达标时是否接受有条件路径 | 是 |

## 4. 功能范围

### 4.1 后续实现应覆盖的用户流程

- 未登录访问智能推荐：展示登录前置状态、登录或注册入口、简短说明推荐需要学生画像，不展示推荐列表。
- 登录后画像不完整：展示画像缺失项、完善画像入口和保存后重新推荐的路径，不展示默认推荐列表。
- 登录后画像完整：按用户画像生成推荐结果，展示推荐专业、学校、层次、费用或预算匹配、语言匹配、学术匹配、风险提示和推荐理由。
- 画像修改后重新推荐：推荐结果应基于最新已保存画像重新计算，不能继续展示旧画像下的缓存结果。
- 登录状态变化：退出登录后应清除或隐藏账号级推荐结果，避免不同用户之间泄露画像或推荐内容。
- 错误和空状态：如果画像完整但没有匹配专业，应解释原因并引导用户调整画像，而不是展示无依据的兜底推荐。

### 4.2 后续实现应覆盖的模块

- 用户端智能推荐入口和推荐弹窗。
- 规划页推荐结果区和学生画像入口。
- 登录弹窗与智能推荐入口之间的跳转或回到原入口的状态。
- 学生画像保存、读取、完整度判断和缺失项提示。
- 推荐 API 的权限、入参、缓存策略和结果解释字段。
- 共享类型中与推荐请求、画像完整度、推荐结果解释和推荐风险相关的契约。
- 必要时补充管理端推荐规则维护边界，但不在 TASK-063 文档任务中实现。

## 8. 后续实现验收口径

后续 TASK-065 实现时，至少需要满足以下验收口径：

- 未登录用户打开智能推荐入口时，只能看到登录或注册引导，不能看到专业推荐列表、默认推荐卡或个性化匹配分数。
- 登录后但画像不完整时，系统明确提示缺失画像项，并引导补充画像；仍不能展示专业推荐列表。
- 画像完整后，推荐请求必须使用当前登录用户已保存的画像字段，推荐结果必须能展示至少一组与画像字段相关的匹配理由。
- 修改画像并保存后，推荐结果重新计算或刷新，不继续使用旧画像缓存。
- 退出登录或切换账号后，旧账号推荐结果不可见；新账号只能看到自己的画像和推荐。
- 推荐接口、前端状态和缓存 key 不应允许匿名用户伪造个性化推荐请求。
- 无匹配专业时展示可解释空状态，说明预算、层次、专业方向、GPA 或语言条件可能导致无结果。
- 浏览器验证应覆盖桌面和移动端的未登录、画像缺失、画像完整和退出登录状态；如涉及多语言，至少覆盖中文和英文提示。

## 10. 需要人工确认的问题

- 学生画像最低完整度是否采用 TASK-008 字段，还是需要新增意向国家、入学时间、学历背景、专业偏好权重、语言考试类型等字段。
- 未登录用户是否允许填写本地画像草稿，但不展示推荐结果；还是必须先登录才能填写画像。
- 登录后是否自动合并访客本地画像草稿，还是要求用户手动确认覆盖或合并。
- 智能推荐是否只允许账号级服务端画像，还是允许前端临时传入未保存画像做一次性推荐预览。
- 当前 `GET /api/programs/recommendations` 这类公开推荐接口是否需要改名、加鉴权或拆分为公开筛选与个性化推荐两个接口。
- 画像完整但无推荐结果时，产品希望优先提示调整哪些条件：预算、GPA、语言成绩、专业方向还是学历层次。
- 推荐理由需要展示到什么粒度：仅展示命中标签，还是展示分数、风险项、费用差额、语言差距和申请层级。
- 后续是否需要管理端配置推荐规则、画像字段字典和推荐结果权重。

## 12. 风险和后续实现边界

- 从访客可用推荐改为登录前置可能降低即时体验，后续设计需要提供清晰的登录价值说明和回到原推荐入口的路径。
- 如果画像完整度规则过严，用户可能长期卡在完善画像前；如果规则过松，推荐仍可能缺少依据。
- 如果继续沿用匿名推荐 API 或只在前端隐藏结果，可能被直接调用接口绕过登录门槛。
- 如果推荐结果缓存没有包含用户 ID、画像版本或画像字段摘要，可能出现画像变更后推荐不刷新或跨用户结果污染。
- 学生画像包含个人申请意向和学术信息，后续实现需要注意账号隔离、退出登录清理、错误日志和本地缓存隐私。
- 当前工作区存在大量未提交改动，后续实现和提交需要严格区分 TASK-064、TASK-065、TASK-066 与历史改动，避免把无关文件混入验收和 commit。
