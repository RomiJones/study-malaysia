## 2. 结论摘要

静态 HTML 已经把收藏、规划工具、用户画像、费用估算、智能推荐、申请任务、签证清单和登录弹窗串成完整用户闭环。其核心特征不是单个页面，而是一组以 localStorage 为基础的轻量状态：未登录用户也能收藏、填写画像、生成推荐、形成申请组合和记录材料或签证进度；登录只是把本地会话提升为可持久化账户状态。

旧系统已经具备相关雏形：用户端有收藏页、规划页、费用估算弹窗、推荐弹窗和登录弹窗；后端有收藏服务、规划服务、推荐接口、费用估算接口和申请管理实体；管理端有申请管理页面和跟进记录。但当前实现与静态页仍有明显差距：规划页强制登录，用户画像类别仍固定为 7 类，收藏未实现登录后本地状态合并，申请任务缺少静态页的冲刺/主申/保底自动分层，费用估算与推荐弹窗视觉不一致，管理端无法维护画像策略、材料模板、任务阶段和推荐规则。

后续实现必须以静态 HTML 为用户端视觉基准，尤其是规划五标签页、画像表单、进度条、材料状态、申请任务卡片、费用估算弹窗、智能推荐弹窗、登录弹窗、收藏空状态和浮动按钮。后端与管理端应补齐持久化、配置化和跟进管理能力，避免把 Notion 或静态 HTML 当作业务运行时数据源。

## 3. PRD

### 3.1 背景

TASK-008 聚焦静态页面中已经验证过的用户留存与申请推进能力：收藏用于沉淀候选院校和专业，用户画像用于驱动推荐和规划结果，申请规划器用于把推荐结果转成可执行的材料、任务和签证清单，登录弹窗用于把未登录本地状态升级为账户持久化状态。

旧系统当前具备 Vue 3 用户端、NestJS API、Element Plus 管理端和 shared 类型基础，但这些能力仍偏基础实现，未完整还原静态页的交互、视觉、状态策略和三端协同。

### 3.2 目标

- 明确收藏、规划工具、用户画像、费用估算、智能推荐、申请任务、签证清单和登录弹窗的产品规则。
- 明确未登录本地会话与登录后服务端持久化的合并策略。
- 明确用户画像字段如何驱动推荐、材料清单、申请任务和费用估算。

- 明确旧系统用户端、后端服务、管理端与静态 HTML 的差距。
- 把后续任务按用户端、后端服务、管理端拆成中文任务项。
- 明确后续用户端实现必须与静态 HTML 视觉 1:1 一致，并保留浏览器截图验证。

## 4. 静态 HTML 功能分析

### 4.1 状态与本地持久化

静态页以全局状态 `S` 管理 TASK-008 相关能力，并用 localStorage 保存关键状态：

| 存储键 | 状态内容 | 静态页用途 |
| --- | --- | --- |
| `studymy_favorites` | 收藏院校和收藏专业 ID | 导航数量、收藏页、院校卡片、专业详情弹窗 |
| `studymy_profile` | 用户画像 | 推荐、材料清单、准备度、申请任务 |
| `studymy_material_progress` | 材料状态 | 材料清单状态选择 |
| `studymy_application_tasks` | 申请任务列表 | 申请管理卡片 |
| `studymy_visa_checklist` | 签证清单状态 | 签证清单完成勾选 |
| `studymy_user_auth` | 模拟登录状态 | 导航、会员中心、登录弹窗 |
| `studymy_compare` | 对比院校列表 | 与 TASK-007 对比能力共用 |

静态页会对旧 localStorage 数据做运行时归一化，防止旧结构破坏页面渲染。后续实现也应保留版本兼容和容错逻辑，例如数组、对象、布尔值和枚举值的兜底。

### 4.2 收藏能力

静态页支持院校和专业两类收藏：

- 院校卡片心形按钮可以收藏或取消收藏院校。
- 专业详情弹窗按钮可以收藏或取消收藏专业。
- 导航收藏入口显示收藏总数。
- 收藏页分为收藏的院校和收藏的专业两块。
- 收藏为空时显示居中空状态，引导用户回到院校库添加收藏。
- 收藏状态未登录即可保存到本地，刷新页面不丢失。

后续产品策略应为：

- 未登录：使用 localStorage 保存收藏，键名可兼容静态页。
- 登录后：通过后端收藏 API 保存到 MySQL。
- 登录瞬间：本地收藏与服务端收藏做并集合并，重复项去重。
- 退出登录：保留本地缓存作为访客状态，但不得泄露其他账号的服务端收藏。
- 后端返回：收藏接口应返回完整院校和专业摘要，避免用户端只靠 ID 重建页面。

### 4.3 用户画像

静态页默认画像为：

| 字段 | 默认值 | 用途 |
| --- | --- | --- |
| `level` | 硕士 | 匹配专业层次，生成不同材料清单 |
| `targetCategory` | IT | 匹配专业类别，生成推荐和申请任务 |
| `budget` | 80000 | 判断年度总成本是否匹配 |
| `gpa` | 2.9 | 判断学术门槛 |
| `ielts` | 5.5 | 判断语言门槛 |
| `experience` | 0-1年 | 用于画像完整度和后续咨询判断 |
| `acceptNoLanguage` | true | 语言未达标时判断是否接受先申请后补语言 |

静态页目标专业类别不是旧系统固定 7 类，而是从所有院校专业中动态提取。后续应将专业类别改为可维护字典或可扩展枚举，避免推荐和筛选被旧类型限制。

### 4.4 智能推荐与规划结果

静态页推荐逻辑以画像字段驱动：

- 只匹配 `publicDisplayStatus === "ready"` 的专业。
- 按学历层次和目标专业类别筛选专业。
- GPA 达到要求加分，接近要求给较低加分。
- IELTS 达标加分；未达标但学校支持免语言或后补语言且用户接受时给条件录取加分。
- 年总成本在预算内加分，预算上浮 20% 内给较低加分。
- QS 排名靠前额外加分。
- 推荐结果按分数排序，最多 8 条。
- 规划概览只展示前 3 条，并标注冲刺、主申、保底。

后续应把推荐结果拆为可解释模型：总分、分项命中、风险原因、费用匹配、语言匹配、学术匹配、排名加分和推荐层级。用户端需要展示简洁结果，管理端需要能调整规则。

### 4.5 规划器五标签页

静态页规划器包含五个标签页：

- **申请概览**：准备度、材料完成数、目标层次、年度预算和智能推荐。
- **学生画像**：学历、专业类别、GPA、IELTS、预算、工作经验、是否接受后补语言。
- **材料清单**：按申请层级生成材料，支持状态选择。
- **申请管理**：根据推荐自动生成申请任务，展示分层、阶段、进度、学校、专业和年总成本。
- **签证清单**：展示 offer、押金、签证材料、签证获批、行前准备等步骤，点击切换完成状态。

旧系统 PlannerPage 已有相似标签，但当前强制登录，视觉不一致，且任务生成、材料模板和状态合并策略仍需补齐。

### 4.6 材料清单规则

静态页基础材料包括：

- 护照首页扫描件。
- 白底证件照。
- 英文版成绩单。
- 英语成绩证明。

按学历层次追加：

- 本科：高中毕业证或在读证明、个人陈述。
- 硕士：本科毕业证与学位证、个人陈述或 Study Plan、推荐信 1-2 封。
- 博士：硕士学位材料、研究计划书、学术简历或论文成果。

材料状态包括：

- `done`：已完成。
- `progress`：准备中。
- `wait`：待准备。
- `draft`：待起草。

后续应将材料模板从硬编码升级为后端配置，管理端可按学历层次、学校、专业、申请轮次维护默认材料。

### 4.7 申请任务规则

静态页申请任务在用户没有任务时自动从推荐结果前 4 条生成：

- 第 1 条为冲刺。
- 第 2 到第 3 条为主申。
- 第 4 条为保底。
- 默认阶段依次为待创建、材料准备中、待递交、院校审核中。
- 默认进度依次为 20%、45%、70%、82%。
- 任务卡展示分层标签、阶段标签、专业名、学校名、年总成本和进度条。

后续应把自动生成和手动加入规划拆开：

- 从推荐结果自动生成申请组合时，需要用户确认后保存。
- 专业详情“加入申请规划”应创建或更新对应任务。
- 任务阶段、进度和下一步动作应由服务端持久化。
- 管理端应能查看和跟进正式申请记录，同时区分用户自助规划任务与后台正式申请单。

### 4.8 费用估算

静态页费用估算弹窗是纯输入工具：

- 年学费。
- 年生活费。
- 学制。
- 其他费用。
- 计算总费用、年学费合计、年生活费合计、其他费用和年总成本。

旧系统费用估算已接入 `/programs/cost-estimate/:id`，以院校和专业选择为入口，但视觉不一致，且静态页的自由输入能力缺失。后续应支持两种模式：

- 快速估算：按静态页输入四个数值即时计算。
- 专业估算：选择院校和专业后带入官方费用、学制和生活费默认值，允许用户调整。

### 4.9 登录弹窗与会话升级

静态页登录弹窗包含登录和注册两个 tab：

- 桌面端居中，移动端贴底。
- 邮箱或手机号输入。
- 密码输入。
- 注册模式增加昵称。
- 静态页只模拟登录状态。

旧系统已有真实认证接口和 token 存储。后续需要补齐的是登录前后状态衔接：

- 登录前允许使用收藏、画像、材料、任务和签证清单。
- 登录后触发本地状态与服务端状态合并。
- 合并完成后用户端刷新本地缓存为服务端结果。
- 登录失败不得清空本地规划。
- 注册成功后同样执行合并。

## 6. 视觉规范

后续用户端实现必须以静态 HTML 为唯一视觉基准，并复用或等价实现 TASK-002 中的全局 token、字体、圆角、阴影、按钮、表单、弹窗、卡片和响应式断点。

### 6.1 收藏视觉

- 收藏空状态居中，内边距 `60px 24px`。
- 空状态图标约 `48px`，下方为标题和弱文本。
- 收藏院校复用静态页横向院校卡片视觉。
- 收藏专业卡片需要保留白底、`1px` 边框、`16px` 圆角和轻阴影。
- 收藏按钮激活态使用红色语义，取消操作也使用红色提示。

## 8. 持久化与状态合并策略

### 8.1 推荐策略

- 访客态继续使用 localStorage 保存收藏、画像、材料、申请任务和签证清单，保证低门槛体验。
- 登录态以 MySQL 为最终运行时数据源，通过 API 返回服务端状态。
- 登录或注册成功后执行一次合并，合并结果覆盖本地缓存。
- Notion 只保存中文任务和项目文档，不参与运行时状态存储。

### 8.2 合并规则

| 数据 | 合并策略 |
| --- | --- |
| 收藏院校 | 本地与服务端取并集，按最近收藏时间排序，重复 ID 去重 |
| 收藏专业 | 本地与服务端取并集，按最近收藏时间排序，重复 ID 去重 |
| 用户画像 | 如果本地画像由用户修改过，优先本地；否则保留服务端；冲突字段记录合并来源 |
| 材料状态 | 同一 key 取进度更高状态，状态顺序为 draft、wait、progress、done |
| 申请任务 | 按 `universityId + programId` 去重；同一任务取更高进度和最新阶段 |
| 签证清单 | 布尔值取或，有一端完成即完成 |
| 费用估算输入 | 不强制服务端保存，保留最近一次本地输入；专业估算可保存快照 |

### 8.3 失败处理

- 登录失败不得清空本地状态。
- 合并接口失败时保留本地状态，并提示稍后同步。
- 合并成功后写入服务端返回的规范化状态，避免用户端继续持有旧结构。
- 对旧 localStorage 结构必须做归一化，防止空值、错类型和旧枚举导致页面崩溃。
